## 三、功能演示 + 对应后端代码讲解（约 4-5 分钟）

### 3.1 产品列表 API

> **画面**：前端展示产品列表，同时切到 `server/src/products/products.service.ts`

**讲解词**：

> 先看产品列表。前端请求 `GET /api/products`，我实现的接口支持按品类筛选、关键词模糊搜索、多维度排序。
>
> **关键设计**：用 `MAX(id)` 而非 `MAX(recorded_at)` 获取最新价格，避免同一秒多条记录导致重复行——这是数据库查询的一个细节优化。

### 3.2 爬虫调度机制（重点）

> **画面**：展示 NestJS `crawl.service.ts` 的 taskId 管理 + spawn 调用

**讲解词**：

> 爬取功能的前端操作很简单——输入关键词、选品类、点搜索。但背后的**调度机制**是我设计的关键点。
>
> 用户发起爬取请求后，NestJS 通过 `child_process.spawn` **异步启动 Python 进程**，立即返回一个 **taskId**。前端轮询 `GET /api/crawl/status/:taskId` 获取进度。
>
> 为什么用 spawn 而不是直接调 Python 函数？因为爬虫是耗时 I/O 操作，如果同步等待，整个服务会阻塞。异步 spawn 让 NestJS 在后台等爬虫结果，同时继续处理其他请求。
>
> 这里有一个设计取舍：taskId 存在内存 Map 中，服务重启会丢失。但爬取任务通常 5-15 秒就完成，持久化到数据库收益低，所以这是有意识的选择。

### 3.3 预览-确认流程

> **画面**：展示爬取结果预览 + 确认保存的流程

**讲解词**：

> 爬虫以 `--preview` 模式运行，结果先通过 JSON stdout 返回前端展示。用户审核确认后，我再调 `save.py` 写入数据库。
>
> JSON stdout 通信的好处：数据不走命令行参数，不受长度限制，也不需要转义特殊字符。
>
> 这个**预览-确认机制**是我和后端爬虫模块衔接的核心设计——用户确认前，数据不会进库。

### 3.4 统计分析 API

> **画面**：展示仪表盘统计卡片

**讲解词**：

> 仪表盘的四个统计卡片——总数、均价、最低价、最高价——数据来自我写的 Stats 模块。
>
> **核心 SQL**：通过子查询取每个产品的最新价格，然后按品类 `GROUP BY` 聚合。这是典型的"取最新记录后再分组"场景。

### 3.5 AI 模块（重点）

> **画面**：展示 AI 对话 + AI 设置页面 + 代码中的 LLMProvider 接口

**讲解词**：

> AI 模块是我独立设计的部分。采用了**策略模式**——定义一个 `LLMProvider` 接口：
>
> ```typescript
> interface LLMProvider {
>   chat(messages: Message[]): Promise<string>;
>   chatStream(messages: Message[]): AsyncGenerator<StreamChunk>;
> }
> ```
>
> `OpenAIProvider` 和 `AnthropicProvider` 分别实现这个接口。用户可以在设置页面自由切换提供商和模型，甚至填入国内模型的 OpenAI 兼容接口地址。
>
> 系统内置四种分析模式：
>
> | 模式 | 功能 | 说明 |
> |------|------|------|
> | query | 查价格 | 根据数据库数据回答硬件价格问题 |
> | predict | 预测走势 | 分析波动幅度、历史区间、季节性规律 |
> | report | 生成报告 | 结构化市场分析：趋势 + 品类动态 + 购买建议 |
> | compare | 产品对比 | 多维度性价比对比 |
>
> AI 在回答前会查询数据库获取相关产品数据，作为上下文注入提示词，所以回答基于**真实数据**，不是凭空生成。
>
> 两种提供商都实现了 SSE 流式输出，前端打字机效果体验一致。

## 四、遇到的挑战（约 1 分钟）

**讲解词**：

> 我在后端开发中遇到的主要挑战有两个：
>
> **第一，跨语言进程通信。** NestJS 是 TypeScript，爬虫是 Python，它们怎么配合？最终方案是 `child_process.spawn` + JSON stdout + taskId 轮询，异步非阻塞架构。
>
> **第二，AI 多提供商兼容。** OpenAI 和 Anthropic 的 API 格式完全不同——OpenAI 用 `/chat/completions`、Anthropic 用 `/v1/messages`，消息格式也不同。通过策略模式抽象出统一接口，各自内部处理差异，上层调用无感。

## 附录 B：老师常见追问 + 回答要点

### Q1：为什么 NestJS 而不直接用 Flask/Django？

> 答：Node.js 事件驱动模型适合高并发 I/O，NestJS 的依赖注入和模块化架构适合多人协作。我们团队前端也是 JS/TS，语言统一减少沟通成本。

### Q2：taskId 存在内存里，重启就丢了吧？

> 答：是的，有意识的设计取舍。爬取任务 5-15 秒完成，持久化收益低。需要的话可以改用 Redis，但目前场景不需要。

### Q3：confirmSave 为什么用 stdin 传数据？

> 答：避免命令行长度限制（Windows 8191 字符）和 shell 转义问题。管道传输无长度限制，更安全。

### Q4：价格历史查询为什么用 MAX(id) 而不是 MAX(recorded_at)？

> 答：同一秒可能有多条记录，MAX(recorded_at) 会返回多行导致 JOIN 重复。id 是自增主键，MAX(id) 保证唯一。

### Q5：AI 双提供商是怎么实现的？

> 答：策略模式。定义 LLMProvider 接口，OpenAIProvider 和 AnthropicProvider 分别实现。用户在前端切换，后端工厂方法返回对应实例。

### Q6：这个系统里你最自豪的设计是什么？

> 答：AI 双提供商架构 + 爬虫异步调度机制。策略模式让 AI 模块灵活可扩展，异步 spawn + taskId 轮询让爬虫不阻塞服务。
